1. Общая концепция
Вся логика генерации дорог, определения событий и построения маршрутов перенесена на сервер и базу данных. Клиент (Unity) выступает только как интерфейс для выбора миссии, транспорта и груза, отображения результатов и визуализации перемещения. Сервер (C# .NET) управляет данными, выполняет расчёты и обеспечивает детерминизм через фиксацию событий в БД на период сессии или перегенерации.

2. Компоненты системы
2.1. База данных (PostgreSQL + PostGIS)
Основное хранилище всей информации. Ключевые таблицы:

nodes – узлы дорожной сети (перекрёстки, точки старта/финиша). Поля: id (bigint), geom (point), name (опционально).

segments – рёбра графа (участки дорог). Поля:

id (double precision) – уникальный идентификатор сегмента.

start_node_id (foreign key to nodes),

end_node_id,

length (float) – расстояние в км,

max_speed (float) – ограничение скорости (если нужно),

event_type_id (foreign key to event_types, может быть NULL) – текущее событие на сегменте,

event_value (float) – параметр события (например, дополнительные секунды или процент замедления),

last_updated (timestamp) – для отслеживания актуальности событий.

event_types – справочник типов событий:

id (serial),

name (text),

effect_type ('percent' или 'fixed'),

default_probability (float),

effect_range_min, effect_range_max (для генерации значения),

description.

vehicles – транспорт:

id, name, base_speed (км/ч), price_per_km, load_time (сек), unload_time (сек), allowed_cargo_types (JSON или связь).

cargos – грузы:

id, name, speed_factor, price_multiplier, load_time_modifier, unload_time_modifier.

missions – миссии:

id, name, start_node_id, end_node_id, allowed_vehicles (JSON), allowed_cargos (JSON), time_limit (сек, NULL если нет), base_reward, penalty_fixed (штраф за опоздание), is_active.

user_progress – прогресс игрока:

user_id, mission_id, status (available, accepted, completed, failed), accepted_at, deadline, result (JSON с результатами последнего расчёта) и т.д.

global_settings – настройки:

key, value – например, текущие вероятности событий (могут переопределять default_probability).

2.2. Сервер (C# .NET)
API endpoints:

POST /api/session/start – инициализация сессии:

Принимает userId.

Загружает из БД:

список доступных миссий (для данного пользователя, с учётом прогресса),

справочники транспорта и грузов,

текущие настройки вероятностей событий (из global_settings или event_types).

Важно: на этом этапе сервер не генерирует события для сегментов. Генерация событий может происходить либо заранее (периодический процесс), либо динамически при первом запросе маршрута (с сохранением в БД для фиксации на сессию). Выбор стратегии зависит от требований к производительности и частоты обновления.

Возвращает клиенту JSON с миссиями, транспортом, грузами и настройками (без событий).

POST /api/route/calculate – расчёт маршрута:

Принимает: missionId, vehicleId, cargoId.

По missionId получает из БД start_node_id и end_node_id, а также допустимые транспорты и грузы. Проверяет, что выбранные vehicleId и cargoId разрешены.

Вызывает функцию БД (например, с использованием pgRouting) для поиска пути между узлами. Функция возвращает:

список segment_id в порядке следования,

общую длину пути.

Для каждого полученного segment_id извлекает из таблицы segments текущее событие (event_type_id, event_value). Если событие не задано (NULL), считаем, что его нет.

На основе данных о транспорте, грузе, длине сегментов и событиях рассчитывает:

время в пути с учётом погрузки/разгрузки и влияния событий,

стоимость (базовая + возможный штраф за опоздание, если travelTime > time_limit).

Формирует ответ, включающий:

travelTime (сек),

finalCost (валюта),

segments – массив с деталями: segmentId, eventType (если есть), eventValue, timeContribution (время прохождения сегмента с учётом события).

Обновляет прогресс миссии: если миссия ещё не была принята, меняет статус на accepted и записывает deadline (текущее время + travelTime, если миссия с лимитом, иначе NULL). В случае уже принятой миссии можно просто возвращать результат, не меняя статус (доставка считается мгновенной). По желанию можно реализовать логику фактического завершения миссии после расчёта.

Возвращает ответ клиенту.

(Опционально) POST /api/admin/regenerate-events – административный endpoint для перегенерации событий на всех или выборочных сегментах на основе текущих вероятностей. Запускает фоновый процесс, который обновляет поля event_type_id и event_value в таблице segments. Это позволяет менять частоту событий для обучения.

Сервисы на сервере:

Менеджер миссий – загрузка, проверка доступности, обновление прогресса.

Калькулятор пути – взаимодействие с БД для получения маршрута и событий, расчёт времени и стоимости.

Генератор событий – используется при перегенерации событий в БД. Принимает список сегментов, вероятности событий из global_settings, для каждого сегмента с помощью генератора случайных чисел определяет тип события и его параметр (интенсивность) в заданном диапазоне. Результат сохраняется в таблице segments.

2.3. Клиент (Unity)
Менеджер сессии:

При запуске отправляет запрос на session/start, получает миссии, транспорты, грузы. Сохраняет их в локальных структурах.

Отображает список миссий, позволяет выбрать одну.

UI выбора транспорта и груза:

После выбора миссии показывает только разрешённые для неё транспорт и груз (данные получены от сервера).

Отправка запроса на расчёт:

По нажатию кнопки "Рассчитать" отправляет missionId, vehicleId, cargoId на route/calculate.

Обработка ответа:

Получает travelTime, finalCost, список сегментов с событиями.

Отображает итоговое время и стоимость.

Если нужно визуализировать маршрут на карте, использует полученные segmentId для подсветки соответствующих сегментов (предполагается, что клиент имеет локальную копию геометрии дорог или может запросить координаты сегментов отдельно). Для простоты можно сначала загрузить все сегменты (их геометрию) при старте, чтобы иметь возможность отрисовать маршрут.

Визуализация событий:

Для каждого сегмента в ответе есть информация о событии. Клиент может отобразить иконку пробки, ремонта и т.п. рядом с сегментом.

3. Детерминизм и фиксация событий
События на сегментах фиксированы на момент генерации дорог. Поскольку дорожная сеть статична (или перегенерируется только администратором), события хранятся прямо в таблице segments. Это гарантирует, что для любого маршрута, запрошенного в любой момент времени, события будут одними и теми же, пока не будет запущена процедура перегенерации.

Как обеспечивается неизменность в рамках сессии?
Если перегенерация событий происходит редко (например, раз в день), то все игроки видят одну и ту же картину. Если требуется изменять вероятность событий для обучения, администратор может запустить перегенерацию с новыми параметрами. При этом старые данные заменяются, и все последующие запросы будут использовать новые события.

Альтернативный подход (для более тонкого контроля):

При старте сессии сервер может клонировать текущие события в отдельную таблицу session_segments, привязанную к sessionId, и работать с ней. Это позволяет разным игрокам иметь разные наборы событий (например, для A/B тестирования). Однако это сложнее и требует больше ресурсов.

4. Расчёт времени и стоимости
Формулы (на сервере):

Пусть:

V – базовая скорость транспорта (км/ч),

cargo.speedFactor – множитель скорости груза,

dist_i – длина i-го сегмента (км),

event на сегменте: если тип percent с коэффициентом p (например, 0.3 = +30%), то время на сегменте = (dist_i / (V * cargo.speedFactor)) * 3600 * (1 + p). Если тип fixed с дополнительными секундами t_add, то время = (dist_i / (V * cargo.speedFactor)) * 3600 + t_add.

loadTime = vehicle.load_time + cargo.load_time_modifier,

unloadTime = vehicle.unload_time + cargo.unload_time_modifier.

Общее время:
travelTime = loadTime + unloadTime + sum(time_i).

Базовая стоимость:
baseCost = totalDistance * vehicle.price_per_km * cargo.price_multiplier + vehicle.base_fee + cargo.handling_fee (если такие поля есть; можно упростить).

Штраф за опоздание (если миссия имеет time_limit и travelTime > time_limit):
penalty = mission.penalty_fixed (или процент от baseCost, заданный в миссии).
Итог: finalCost = baseCost - penalty (не менее 0).

Если миссия имеет фиксированную награду base_reward, то finalCost = base_reward - penalty.

5. Взаимодействие с БД для поиска пути
Используется PostgreSQL с расширением pgRouting. Предположим, таблица segments содержит колонки id, source (start_node_id), target (end_node_id), length (cost). Тогда функция поиска кратчайшего пути может выглядеть так:

sql
SELECT seq, node, edge, cost
FROM pgr_dijkstra(
    'SELECT id, source, target, length AS cost FROM segments',
    start_node_id, end_node_id
);
Она вернет последовательность рёбер (edge = segment_id). Общая длина – сумма cost.

Альтернативно, можно написать хранимую функцию, которая сразу возвращает массив segment_id[] и общую дистанцию.

6. Обработка ошибок и валидация
Если путь между start_node и end_node не существует (БД возвращает пустой результат), сервер возвращает ошибку "Маршрут не найден".

Если выбранный транспорт или груз не разрешены миссией – ошибка.

Если миссия уже завершена или недоступна – ошибка.

Лимиты запросов – не более N запросов в минуту от одного пользователя.

8. Расширяемость новыми событиями
В БД добавляется запись в event_types.

В административном интерфейсе (или через API) можно обновить настройки вероятностей.

При следующей перегенерации событий (ручной или по расписанию) новые типы начнут появляться на сегментах.

Клиент должен уметь отображать неизвестные типы событий (например, по ID или по переданному названию). В ответе сервера можно включать не только eventType (строковый идентификатор), но и локализованное название, иконку (ссылку) – для гибкости.

9. Управление вероятностями для обучения
Администратор может через API изменять значения в global_settings (например, traffic_probability = 0.2) и затем запускать перегенерацию событий. Либо можно сделать так, что при каждом запросе маршрута сервер использует текущие вероятности для динамического определения событий, но при этом сохраняет результат в сессионном кэше, чтобы в рамках одной сессии события не менялись. Однако это сложнее. Рекомендуется первый вариант: периодическая перегенерация всей карты событий с нужными вероятностями.

10. Заключение
Предложенная архитектура полностью соответствует новым требованиям:

Клиент не генерирует дороги и не вычисляет события.

Маршруты строятся на сервере с помощью БД.

События хранятся в БД и фиксированы на момент генерации.

Сервер выполняет расчёт времени и стоимости с учётом событий.

Миссии управляются через БД, включая ограничения на транспорт и грузы.

Система легко расширяется новыми типами событий и настройкой их вероятностей.

Реализация не требует сложной синхронизации через seed и полностью исключает возможность клиентских читов, так как все проверки выполняются на сервере.
